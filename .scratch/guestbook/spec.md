# 미니 방명록

Status: ready-for-agent

## Problem Statement

방문자가 이름과 메시지를 남기고 다른 사람이 남긴 방명록 글을 볼 수 있는 곳이 없다. 회원가입이나 로그인을 요구하면 한 줄 남기려는 방문자에게 부담이 너무 크다. 반대로 아무 권한 확인 없이 열어 두면 누구나 남의 방명록 글을 고치거나 지울 수 있다. 가입 없이 쓰면서도 자기 글만 관리할 수 있어야 한다.

## Solution

한 페이지짜리 방명록을 만든다.

- 방문자는 이름, 메시지, 비밀번호만 입력하면 방명록 글을 남길 수 있다.
- 모든 방명록 글은 작성 시각이 최신인 것부터 한 페이지에 모두 보인다.
- 방명록 글을 고치거나 지울 때는 그 글을 쓸 때 정한 비밀번호를 다시 입력한다.
  - 비밀번호가 맞으면 메시지를 고치거나 글을 지울 수 있다.
  - 틀리면 요청이 거부되고, 거부된 이유가 그 방명록 글 바로 옆에 표시된다.
- 이미 삭제된 방명록 글에 대한 요청은 비밀번호 불일치와 구분해서 안내한다.

## User Stories

### 작성

1. 방문자로서, 가입이나 로그인 없이 방명록 글을 남기고 싶다. 그래야 부담 없이 한마디 남길 수 있다.
2. 방문자로서, 방명록 글에 내 이름을 적고 싶다. 그래야 누가 남긴 글인지 다른 사람이 알 수 있다.
3. 방문자로서, 메시지를 여러 줄로 쓰고 싶다. 그래야 줄바꿈이 필요한 긴 인사를 남길 수 있다.
4. 방문자로서, 글을 쓸 때 비밀번호를 정하고 싶다. 그래야 나중에 내 방명록 글만 고치거나 지울 수 있다.
5. 방문자로서, 이름이나 메시지나 비밀번호를 비우거나 공백만 넣으면 어느 항목이 문제인지 안내받고 싶다. 그래야 무엇을 고쳐야 할지 안다.
6. 방문자로서, 이름은 20자, 메시지는 500자, 비밀번호는 4–32자라는 제한을 넘기면 안내받고 싶다. 그래야 제한에 맞게 고칠 수 있다.
7. 방문자로서, 입력이 거부되더라도 이미 쓴 내용이 지워지지 않았으면 좋겠다. 그래야 처음부터 다시 쓰지 않아도 된다.
8. 방문자로서, 남긴 방명록 글이 목록 맨 위에 바로 나타났으면 좋겠다. 그래야 제대로 남겨졌는지 확인할 수 있다.
9. 방문자로서, 글이 남겨진 뒤에는 작성 폼이 비워졌으면 좋겠다. 그래야 같은 글을 실수로 두 번 남기지 않는다.
10. 방문자로서, 다른 사람과 같은 이름을 써도 방명록 글을 남길 수 있었으면 좋겠다. 이름은 표시용일 뿐 신원이 아니기 때문이다.
11. 방문자로서, 이름과 메시지 앞뒤의 공백은 알아서 정리됐으면 좋겠다. 그래야 목록이 깔끔하다.

### 조회

12. 방문자로서, 모든 방명록 글을 한 페이지에서 보고 싶다. 그래야 페이지를 넘기지 않고 전부 읽을 수 있다.
13. 방문자로서, 가장 최근에 남겨진 방명록 글이 위에 오면 좋겠다. 그래야 새 소식을 먼저 볼 수 있다.
14. 방문자로서, 각 방명록 글의 이름, 메시지, 작성 시각을 보고 싶다. 그래야 누가 언제 무슨 말을 남겼는지 안다.
15. 방문자로서, 작성 시각이 한국 시간 기준 `YYYY-MM-DD HH:mm` 형식으로 보이면 좋겠다. 그래야 서버 위치와 상관없이 시각을 헷갈리지 않는다.
16. 방문자로서, 메시지의 줄바꿈이 쓴 그대로 보이면 좋겠다. 그래야 글쓴이가 의도한 모양으로 읽을 수 있다.
17. 방문자로서, 수정된 방명록 글에는 "(수정됨)" 표시가 보이면 좋겠다. 그래야 처음 내용과 달라졌다는 걸 안다.
18. 방문자로서, 방명록 글이 수정돼도 목록 순서가 그대로이면 좋겠다. 정렬은 작성 시각 기준이어야 한다.
19. 방문자로서, 방명록 글이 하나도 없을 때는 비어 있다는 안내를 보고 싶다. 그래야 페이지가 깨진 게 아니라는 걸 안다.
20. 방문자로서, 메시지에 HTML이나 스크립트 같은 문자열이 있어도 글자 그대로 보이면 좋겠다. 그래야 다른 방문자가 안전하다.
21. 방문자로서, 어떤 경로로도 다른 사람의 비밀번호나 그 해시를 볼 수 없어야 한다. 그래야 방명록 글의 권한이 지켜진다.

### 수정

22. 글쓴이로서, 내 방명록 글의 [수정]을 누르면 그 자리에서 메시지 편집창과 비밀번호 입력창이 펼쳐지면 좋겠다. 그래야 다른 화면으로 이동하지 않고 고칠 수 있다.
23. 글쓴이로서, 편집창에 현재 메시지가 미리 채워져 있으면 좋겠다. 그래야 필요한 부분만 고칠 수 있다.
24. 글쓴이로서, 비밀번호가 맞으면 메시지가 바뀌어 목록에 바로 반영되면 좋겠다.
25. 글쓴이로서, 비밀번호가 틀리면 수정이 거부되고 그 방명록 글 옆에 "비밀번호가 일치하지 않습니다"가 표시되면 좋겠다. 그래야 왜 안 바뀌었는지 안다.
26. 글쓴이로서, 비밀번호가 틀려도 편집 중이던 메시지가 남아 있으면 좋겠다. 그래야 비밀번호만 다시 입력하면 된다.
27. 글쓴이로서, 새 메시지도 작성할 때와 같은 규칙(공백만 불가, 500자 이하)으로 검증되면 좋겠다.
28. 글쓴이로서, 편집을 취소하고 원래 상태로 돌아갈 수 있으면 좋겠다.
29. 방문자로서, 다른 사람의 방명록 글은 비밀번호를 모르면 고칠 수 없어야 한다. 그래야 방명록 글을 믿을 수 있다.
30. 글쓴이로서, 수정할 수 있는 건 메시지뿐이어야 한다. 이름, 비밀번호, 작성 시각은 바뀌지 않는다.
31. 글쓴이로서, 이미 삭제된 방명록 글을 고치려 하면 "이미 삭제된 방명록 글입니다"라는 안내를 받고 싶다. 그래야 비밀번호가 틀린 것으로 오해하지 않는다.

### 삭제

32. 글쓴이로서, 내 방명록 글의 [삭제]를 누르면 그 자리에서 비밀번호 입력창이 펼쳐지면 좋겠다.
33. 글쓴이로서, 비밀번호가 맞으면 다시 묻지 않고 바로 지워지면 좋겠다. 비밀번호 입력이 이미 확인 역할을 한다.
34. 글쓴이로서, 지운 방명록 글이 목록에서 바로 사라지면 좋겠다.
35. 글쓴이로서, 비밀번호가 틀리면 삭제가 거부되고 그 방명록 글 옆에 "비밀번호가 일치하지 않습니다"가 표시되면 좋겠다.
36. 방문자로서, 다른 사람의 방명록 글은 비밀번호를 모르면 지울 수 없어야 한다.
37. 글쓴이로서, 이미 삭제된 방명록 글을 지우려 하면 "이미 삭제된 방명록 글입니다"라는 안내를 받고 싶다.
38. 글쓴이로서, 지운 방명록 글이 어디에도 남지 않으면 좋겠다. 삭제는 영구적이다.

## Implementation Decisions

- **스택**: Next.js 16 App Router와 TypeScript를 쓰고, Vercel에 배포한다. 이 Next.js 버전은 API가 바뀐 부분이 있으므로 구현 전에 `node_modules/next/dist/docs/`에서 Server Actions, 폼 상태 처리, 캐시 무효화 부분을 확인한다.
- **방명록 모듈 (핵심, 깊은 모듈)**: 방명록 글에 대한 모든 규칙을 이 모듈 하나가 가진다. 공개 인터페이스는 네 가지 동작이다.
  - 방명록 글 작성(이름, 메시지, 비밀번호)
  - 방명록 글 목록 조회()
  - 메시지 수정(id, 비밀번호, 새 메시지)
  - 방명록 글 삭제(id, 비밀번호)

  각 동작의 결과는 판별 가능한 합 타입이다: 성공 | 입력 오류(항목별 사유) | 비밀번호 불일치 | 이미 삭제된 방명록 글. 입력 검증, 비밀번호 해시와 검증, 권한 판정은 모듈 안에 숨기고 밖으로 노출하지 않는다.
- **저장소 인터페이스**: 방명록 모듈은 저장소 인터페이스에만 의존한다. 필요한 기능은 넣기, 전체 조회(정렬 포함), id로 찾기, 메시지와 수정 시각 갱신, 삭제다. 운영 구현은 Drizzle ORM과 `drizzle-orm/neon-http` 드라이버로 Neon Postgres에 연결하고, 테스트 구현은 메모리에 둔다.
- **목록 조회 결과**: 비밀번호 해시를 절대 포함하지 않는다. 필드는 id, 이름, 메시지, 작성 시각, 수정 시각(없으면 null)이다.
- **스키마**: 방명록 글 테이블 하나.
  - id: 자동 증가 정수
  - 이름: 텍스트
  - 메시지: 텍스트
  - 비밀번호 해시: 텍스트, 솔트 포함
  - 작성 시각: `timestamptz`, 기본값 현재 시각
  - 수정 시각: `timestamptz`, null 허용
- **정렬**: 작성 시각 내림차순으로 정렬하고, 작성 시각이 같으면 id 내림차순으로 정렬한다. 수정 시각은 정렬에 영향을 주지 않는다.
- **비밀번호**: Node 내장 `crypto.scrypt`에 글마다 다른 무작위 솔트를 붙여 해시한다. 비교는 상수 시간으로 한다. 추가 패키지는 쓰지 않는다.
- **입력 검증** (앞뒤 공백을 제거한 뒤 적용):
  - 이름 1–20자
  - 메시지 1–500자, 줄바꿈 유지
  - 비밀번호 4–32자. 비밀번호는 공백을 제거하지 않고 입력 그대로 쓴다.

  서버의 방명록 모듈이 최종적으로 판단하고, 클라이언트의 `maxLength`와 `required`는 보조 수단이다.
- **권한 판정 순서**:
  1. id에 해당하는 방명록 글이 없으면 "이미 삭제된 방명록 글".
  2. 비밀번호가 다르면 "비밀번호 불일치".
  3. 수정일 때는 새 메시지를 검증한다.
- **삭제**: 하드 삭제한다.
- **서버 연결 층**: 작성, 수정, 삭제는 Server Actions가 폼 데이터를 받아 방명록 모듈을 부르고 결과를 폼 상태로 돌려준다. 성공하면 페이지 캐시를 무효화해 목록을 다시 그린다. 목록은 Server Component에서 방명록 모듈로 조회한다. 이 층에는 규칙을 두지 않는다.
- **화면**: 단일 페이지로, 위에 작성 폼, 아래에 목록을 둔다.
  - 각 방명록 글에 [수정]/[삭제] 버튼을 두고, 누르면 그 자리에서 입력창이 펼쳐진다. 모달이나 별도 페이지는 쓰지 않는다.
  - 실패 안내는 해당 폼 근처에 표시하고, 입력값은 남겨 둔다.
  - 작성에 성공하면 폼을 비운다.
  - 시각은 Asia/Seoul 기준 `YYYY-MM-DD HH:mm`으로 서버에서 포맷한다.
- **마이그레이션**: `drizzle-kit generate`로 만든 SQL 마이그레이션 파일을 저장소에 커밋한다. 적용은 로컬에서 수동으로 한다(`db:migrate` 스크립트). 빌드에는 포함하지 않는다.
- **환경**: 개발과 운영이 DB 하나를 같이 쓴다. `DATABASE_URL`은 `.env.local`과 Vercel 환경 변수에 같은 값으로 넣는다.

## Testing Decisions

- **좋은 테스트의 기준**: 방명록 모듈의 공개 동작과 그 결과만 검증한다. 해시 형식, 솔트 길이, 저장소 호출 횟수 같은 내부 구현은 검증하지 않는다. 내부를 바꿔도 동작이 같으면 테스트는 계속 통과해야 한다.
- **테스트 경계는 하나, 방명록 모듈이다**. Vitest로 작성하고, 메모리 저장소를 넣어 DB 없이 실행한다.
- **다룰 시나리오** (예시, 전부 방명록 모듈의 동작으로 검증한다):
  - 작성한 방명록 글이 목록에 나타나고, 비밀번호나 해시는 결과에 없다.
  - 목록이 작성 시각 최신순이고, 같은 시각이면 id가 큰 쪽이 먼저다. 수정해도 순서가 그대로다.
  - 이름, 메시지, 비밀번호가 비었거나 공백뿐이거나 길이 제한을 넘으면 항목별 입력 오류가 나온다.
  - 맞는 비밀번호로 수정하면 메시지와 수정 시각이 바뀌고, 이름과 작성 시각은 그대로다.
  - 틀린 비밀번호로 수정하거나 삭제하면 비밀번호 불일치가 나오고, 방명록 글은 바뀌지 않는다.
  - 맞는 비밀번호로 삭제하면 목록에서 사라진다. 다시 수정하거나 삭제하려 하면 이미 삭제된 방명록 글이 나온다.
  - 이름이 같아도 비밀번호가 다른 두 방명록 글은 서로의 비밀번호로 수정하거나 삭제할 수 없다.
- **테스트하지 않는 것**: Drizzle 저장소 구현과 Server Actions와 화면. 얇은 연결 코드이므로 실제 앱을 띄워 확인한다.
- **기존 사례**: 저장소에 기존 테스트가 없다. 이 스펙의 테스트가 첫 사례가 된다.

## Out of Scope

- 회원가입, 로그인, 소셜 로그인
- 비밀번호 찾기나 변경
- 이름 수정
- 무차별 대입 방지(시도 횟수 제한, CAPTCHA)
- 스팸 필터, 금칙어, 관리자 기능
- 페이지 나눔과 무한 스크롤
- 소프트 삭제와 복구
- 상대 시각("3분 전") 표시와 방문자 시간대별 표시
- 수정 이력 보관
- 개발과 운영 DB 분리
- 배포 때 마이그레이션 자동 적용

## Further Notes

- 용어는 [GLOSSARY.md](../../GLOSSARY.md)를 따른다. "게시물", "작성자", "내용" 같은 말은 쓰지 않는다.

- 무차별 대입 방지를 넣지 않았으므로, 짧은 비밀번호(4자)는 추측될 수 있다. 미니 범위라서 감수하기로 한 위험이다.
